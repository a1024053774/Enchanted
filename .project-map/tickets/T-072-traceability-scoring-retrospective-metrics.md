## Question

每次提交怎么追溯到是谁、用什么干的？主控怎么给执行层打分？复盘怎么跑？埋哪些指标为系统自进化和以后的 Enchanted 打地基？Herdr 期先用哪些？

## Resolution

2026-10-10 grilling 确认。账本 [native-cli-orchestration](../../.grilling/native-cli-orchestration.md) 的 D20、D26、D28–D31 与 C1、C2、C7–C10；设计见 [spec](../specs/native-cli-orchestration-2026-10-10.md) 第 8–10 节。

- **提交追溯**（D20、D26）：每个会话的环境里带任务、attempt、会话、角色、CLI 版本、模型、强度、启动记录号；用环境变量为该会话的 git 指定钩子目录，提交时追加 `A2A-*` 尾注，钩子目录接着调用项目原有的钩子（账本 F11 实测：不写任何配置文件，加 `--no-verify` 也照样追加）。Claude 的原生会话号由启动时的 `--session-id` 指定，Codex 的从 notify 或 rollout 取。门禁核对候选里的每个提交：带本 attempt 尾注的正常；没有尾注的当作用户本人提交，记为人工介入，作为 action 形态的用户输入并标明来源是"推断：缺尾注"；带别的任务尾注的打回。"配置"即启动记录：完整启动参数、角色卡版本、项目当时的提交号，尾注里只写记录号。用户的话："每一次代码提交都应该能追溯到：见文章的7."
- **验收打分**（D28）：只在 attempt 结束时打一次，大多数任务只有一个 attempt，即最终打一次；对话回合和门禁打回不打分，只由脚本自动计数；升级给更强的执行器时，前一个执行器那次也留一条；放弃只记结果与理由，不打分。打分是验收命令（集成或放弃）的参数，不另起一轮提问，缺了就拒收；执行主控的角色卡加一句"验收时顺手打分"。脚本自动填时间、任务卡、项目、CLI、模型、强度、任务类型、复杂度、交付轮数、耗时、人工介入次数、各项检查的打回次数；执行主控填边界纪律与工程品味各 0–3 分，每项写理由，外加一句备注；用户可另补分，单独存一条，不覆盖；词表定了不轻改。用户的话："不能每轮会话都打分吧，做成最终打分比较合适吗？""这个也可以加在主控验收时加一句话，这样不用多一轮额外的提问，包含在验收提问里就行，这样不会花很多 token"。
- **复盘与轨迹归档**（D29）：手动点"立即复盘"，或按周期自动跑（默认每周一 9:00，可改可关）；每次可选 CLI、模型、思考强度，默认 Claude Code、Opus 5.5、medium（用户："默认 opus5.5 medium"）；在普通窗格里跑，用户能看能插话，本身也照样记录；输入由脚本备好（复盘包）；只读代码和数据，只写自己的报告；中文报告存进项目的 `findings/`（没有这个目录的项目存工作台数据目录），改进建议逐条放上面板，用户批了，构思主控才写成 ticket 或改角色卡。后台把它启动的每个会话的原生记录增量复制、压缩，存在本机工作台数据目录，不进 Git。
- **指标**（D30）：原始事件从第一个切片起全记、只追加，指标都从原始事件现算，不单独存计数；采集清单见 spec 第 8 节，含每次交付的改动行数与文件数；缺陷修复类任务卡加"修复对象"字段，逃逸缺陷靠它算，不靠匹配提交说明去猜；第一版四个视图：模型使用分类（项目 → 任务 → 会话）、一次到位率与打回原因、用户的注意力消耗、打分汇总（执行器 × 任务类型）。用户的话："检测指标可以为以后的 enchanted 做一些地基，还有复盘的轨迹数据，但是 token 监控我觉得没必要做了，重复造轮子，可以想一些其他为我的系统自进化埋一些检测指标。比如按项目看，该项目下每个任务用了哪些模型，做一个分类。"
- **Herdr 期先用三样**（D31）：任务卡模板（markdown，不写脚本；brief 从此改叫任务卡）；提交尾注（`scripts/dispatch` 启动 worker 时带环境变量与钩子目录）；验收打分（执行主控验收时顺手写一行到追加式文件，切换时一次性导入后台库，之后不再写文件）。

不做：额度感知调度与额度水位监控（用户："然后额度水位监控这个先不做。"）；token、成本、缓存命中率监控（用户已用 TokenTracker）。
