## What to build

来源：用户 2026-10-23 在本 session 逐字：“如果存储没了就清理不用的项目缓存,然后这些做完后,再去像真实用户一样来使用软件,找出不合理的地方,就像我今天使用了之后找到那些问题一样,就是最起码做到多 agent 分配像 herdr 这样流畅自然,就是真实使用测试你懂吧.这个你可以安排 codex 用 computer use 去测.”

在 T-150～T-154 都完成之后开始。

1. **场景（真实使用，不是夹具脚本）**：一个一次性的小 Git 项目（放内置盘临时目录，不是用户的项目）。像用户那样做完整一轮：打开项目 → 在项目终端里启动 CLI → 申请执行主控 → 在界面批准 → 对主控说一件需要拆成 2～3 个任务的事 → 主控派出多个 worker（含并行）→ 看流程页、侧栏、终端 → 回答 worker 的上报 → 审查 → 集成 → 看记录页、Reflect、指标。再加至少一个“难”的情形：两个任务同时在跑、一个 worker 被打回、用户中途在 worker 窗格里打字、切换窗格与滚动、关掉再重开应用。
2. **谁来测**：Codex worker（gpt-6.1-sol high）用 Computer Use 操作界面，像不知道内部实现的用户那样用。被测应用是它自己启动的隔离 Electron 实例；真实 Claude 部分用 claude-haiku-5-5（既定做法）。
3. **对照标准**：Herdr 里派发多 agent 的体验——开 agent、看到谁在干什么、切换、盯进度、回复，每一步都直接、不卡、不需要看说明或猜。每个觉得别扭的地方都记。
4. **产出**：中文报告进 `findings/`（日期报告，写进 findings/README 索引），每条发现：现象、复现步骤、截图或录屏（按 T-088 归档）、为什么不合理、严重程度、建议；区分 GPT 模型行为、分工协调、工程与证据处理。同时给“Herdr 对照”小结：哪些环节已达到、哪些没有。
5. 发现只报告，不在本票里修；由构思主控汇总给用户后再切修复票。缺陷级、明显的小问题执行主控可按 T-004 自建 ticket，但在 report 里列出。

## 授权与边界

- Computer Use 的代批按 AGENTS.md 既有授权：范围限本票列出的界面验证，只操作 worker 自己启动的隔离 Electron 窗口；不得代批系统设置或隐私授权、登录与密码、付款、发消息或发布内容、操作用户自己的应用或数据、删除文件；遇到这些停下等用户。每次代批记入证据。
- 不碰用户的 Herdr server 与其他 pane，不 push。
- 存储：内置盘不足时清理本项目的构建缓存、测试夹具等不用的项目缓存（用户 2026-10-23：“如果存储没了就清理不用的项目缓存”），先看清目标再删，不删用户的项目与数据，不动未提交的证据。
