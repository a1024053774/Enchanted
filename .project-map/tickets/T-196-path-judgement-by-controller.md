## Question

用户 2026-10-27 反馈“软件的路径拦截太死板,有时候我想跨多个任务来完成一件事,这个再不同的路径下,很别扭,要么就是不行,项目也有添加其他路径的功能,但是不太能用”（[findings U11](../../findings/2026-10-27-two-real-uses.md)）。现有三道限制：

1. 任务卡白名单：交付里改了卡外文件，验收直接打回（`path_boundary_failed`）。
2. 认领防重叠：同一仓库里有未回收 attempt 与新卡路径重叠，认领就拒（`path_overlap`）；已验收、已集成但未回收的 attempt 也算占用。派发已有 `overlap_reason` 可放行，但主控说明写“不传”。
3. 一个任务只属于一个仓库；项目额外目录可写，但改动不进审查与集成。

## Resolution

用户 2026-10-27：“我觉得让主控 agent 判断呢,因为不同任务不一样, 这方面活动的地方很多,我们人为不太好规定死”。对整理后的划分，用户：“对，按这个划分记成决定，改 T-193 并补票，记完停下等我。”

原则沿用 T-070“提示词管判断，脚本管事实”：门禁算出事实并记录，范围上的放行由主控判断并写理由。

- 路径重叠：门禁列出与哪些任务、哪些文件重叠，交主控判断；可并行就写理由放行，否则排队。已验收或已集成的 attempt 不再占用路径（事实，不需判断）。落地 T-197。
- 卡外文件：交付检查不再直接打回，列出卡外改动的文件；主控判断是合理延伸（写理由接受）还是越界（打回）。清单同时给独立审查员；主控打分的“边界纪律”反映这一项。落地 T-198。
- 跨仓库：拆法由主控决定；系统提供主控在多个已打开项目里建任务、派发的能力。额外目录给不给写、给哪些由主控按任务定，说明写明其中改动不经审查与集成。落地 T-193。

仍由脚本硬性把关，主控不能放行：Git 元数据守护；验收文件不被改动（T-080）；集成时的 Git 合并冲突；每次放行必须带理由并记入事件，没写理由不放行。划分依据：主控放行的是做事的范围，不碰验收是否可信。
