## Question

工作台里怎么建立主控、怎么派发 worker？原做法是由编排后台按任务启动受管主控（`controller_start`，需先有任务、隔离 HOME 与凭据副本，只有测试脚本调用，界面没有入口），worker 只能是 Codex（T-069 的 D19 “第一版只支持 Claude Code（主控）与 Codex（worker）”，为构思主控推荐、被采纳的范围，不是用户提出的要求）。

## Resolution

2026-10-21 用户在会话中决定。

用户原话（逐字）：

- “为什么是这么做的?我想做的是和 herdr 一样的,加上权限管理 1. 这种情况你以前是怎么做的能建立主控的?必须通过终端命令才能启动? 2.这种指派 worker 应该可选的,像指派 codex等等其他 cli 都可以,因为都是在 cli 种启动的,有这么死板吗?”
- “1.可以,这个入口应该是我先添加项目后,会显示当前界面在这个路径下,然后我想启动哪个 cli 就用哪个指令启动 cli,他默认就是和一般的终端一样的,当我告诉他你去做主控,派发 worker 时,他能读 skill 或者 mcp 之类的能知道怎么在我们这个系统里派发其他 agent,互相通信,安排身份,设置界限这些”

随后三个问题，用户都选了推荐项：

1. **认领身份要界面批准。** 普通终端里的 agent 用 a2a 命令申请角色（构思主控、执行主控等），Enchanted 显示“窗格 X 申请成为某角色”，用户点批准后生效。之后它的派发、验收等操作都按这个身份经门禁核对。理由：窗格里的模型可能被别的文本诱导而自封主控。
2. **发现方式：终端自带 a2a 命令，并自动挂上 skill。** Enchanted 普通终端的 PATH 里有 `a2a` 命令，任何能执行 shell 的 CLI 都能调用；支持的 CLI 自动挂上使用说明（例如 Claude Code 的插件目录）。不写 `~/.claude`、`~/.codex`，也不往用户的项目仓库里写文件。各家 CLI 支持哪种挂法，先实测再定。
3. **worker 由后台按主控选的 CLI 启动。** 主控用 a2a 命令指定 CLI（Claude Code、Codex……）、模型、强度和任务卡，后台在新窗格里带着该角色的权限参数启动 worker，worker 的权限是真正强制的。

由此改变的既有决定：

- 主控不再由编排后台启动，也不绑定任务。用户在普通终端里自己启动 CLI（用自己的正常配置与登录），身份经认领与批准后绑定到项目。门禁对主控操作的身份核对改为核对“已批准的认领”。
- worker 的 CLI 不再固定为 Codex（取代 D19 中“worker 只用 Codex”这一半）。每家 CLI 用一个启动适配提供同一组能力：模型与强度、不弹批准窗口而越界即拒、可写路径限制、回合开始与结束的结构化信号、会话可续接。第一批仍是 Claude Code 与 Codex；其他家按需加。
- 权限仍在工作台内（T-071 的四层）：对主控，权限来自认领时批准的角色加上 a2a 命令按角色放行的操作；对 worker，还有后台启动时传入的每会话参数。普通终端不认领身份时，它就是普通终端，没有门禁身份。
