## What to build

依据 [决定记录](../proposals/gate-hardening-2026-10-14.md) D1。现在完成条件以 argv 在验证工作区执行，路径边界只看 `paths.allow`/`paths.deny`，`allow: ["."]` 合法；完成条件所依赖的测试和脚本被候选改了，门禁查不出来，验收文件受不受保护只取决于执行主控写卡时记不记得放进 `deny`。

1. **任务卡新字段 `oracle_paths`（验收文件）**：列出完成条件依赖的仓库内测试、脚本、夹具和配置。写法与 `paths` 相同（确切文件路径，或以 `/` 结尾的目录前缀；不允许 `.`、绝对路径、通配符、`..`、`.git`）。
   - 必填，至少一项。执行主控写不出验收文件，说明完成条件只靠 worker 自己的测试，按 spec 第 2 节本来就不合格。
   - 每一项在认领时的起点提交上必须已存在（文件存在，或目录前缀下至少有一个受控文件），否则认领拒收；防止 worker 自己“新建”验收文件。
   - 与 `red_commands[].test_paths` 不得有交集（红态测试由候选新增或修改，验收文件不许改），任务卡校验时拒收。
2. **门禁检查**：机械检查串里，在路径边界之后、跑完成条件之前，比较候选相对起点改动的路径与 `oracle_paths`；有交集就打回，拒收码为 `oracle_modified`，摘要列出被改的路径。这次打回同样写回 worker 窗格、计入 3 次上限。
3. **打回原因单列**：打分事实里的 `rejections` 增加 `oracle` 一项，`oracle_modified` 计入它，不并入 `path_boundary`。
4. **worker 认为验收文件有误**：走问题上报，由主控或用户改卡；worker 角色卡由构思主控在本票关闭时补一句，worker 不改角色卡。
5. 更新 `.project-map/templates/task-card.md` 的字段表（只加本字段及谁填、怎么填）。spec 第 2 节表格和 `CONTEXT.md` 已由构思主控同步加上。
