## Question

工作台不再基于 Synara 的统一层以后，agent 怎么跑、应用怎么搭、旧票与 fork 怎么处置、什么时候把日常派发从 Herdr 挪过来？

## Resolution

2026-10-10 grilling 确认（R4 起在会话"新思路构思"进行，用户回复"确认"）。账本 [native-cli-orchestration](../../.grilling/native-cli-orchestration.md) 的 D1–D7、D10–D13、D16、D18、D19、D32；设计见 [spec](../specs/native-cli-orchestration-2026-10-10.md) 第 1、10、11 节。

- **不用 Synara 的统一层**（D1、D4）：不用它包装各家 CLI 的 provider 层，也不用它给 agent 的 MCP 网关；agent 以各家原生 CLI 的交互终端运行，不用无头模式。用户的话："我觉得不用 Synara的统一网关，只用 synara 这种前端样式框架就行，里面具体的 cli 还是看每家自己的能力，我们只做编排，像 herdr 这样。"
- **工作台**（D2、D16）：新建轻量 Electron 应用，放在本仓库的新目录，借用 Synara 的前端组件与样式（MIT，保留版权声明）。
- **终端**（D7、D12）：自托管；xterm.js 渲染，node-pty 托管，窗格里跑用户的 zsh（登录 shell），在 zsh 里启动各家 CLI。
- **编排后台常驻**（D13）：界面只是连上去看，关掉或重开界面，agent 照常跑。
- **范围**（D18、D19）：数据模型从一开始按"项目 → 任务 → 会话"支持多项目，第一个切片只跑 a2a；第一版只支持 Claude Code（主控）与 Codex（worker、reviewer），其他家以后按需加，每家补启动参数与状态信号。
- **旧票与 fork**（D3、D6、D11）：T-059、T-066、T-067、T-068 作废（superseded）；已关闭的 T-055～T-065 保留为历史，其中 T-064 的后端随之作废，设置页在新工作台重做；fork 只作组件来源，不再跟进上游，不删；fork 上未推送的 `ddb765956`（T-066）保留不推。
- **切换条件**（D10、D32）：用户输入记录、两层主控、问题面板三项，加上第三阶段的新功能（任务卡、门禁检查串与独立审查、worktree、提交尾注、面板收主控提问、验收打分、复盘、原始事件采集与四个指标视图）都在新工作台里能用；用户试用时至少走一遍：一张真实任务卡从派发跑到集成（含独立审查和打分）、在面板上答一次主控的提问、手动跑一次复盘、看一次模型使用分类；用户说"可用"后，日常派发才从 Herdr 挪过来。已做的面板界面、打包格式、处置规则、提醒、通知与设置页换载体重做，不推翻。切换标准沿用用户 2026-10-09 的话："肯定要把我提的功能至少都做的能用了，我才能到 Synara 里用啊"。
- **术语**：工作台改指 a2a 自己的轻量应用；新增编排后台、窗格等，见 [CONTEXT.md](../../CONTEXT.md)。

取代 T-030（工作台基于 Synara fork 并持续跟进上游）。T-032 的"项目 → 任务 → agent 会话"层级要求沿用，它的 M1 各项由本票的切换条件取代。

被否决：只去掉 MCP 网关、保留 Synara 的协议会话（R0 Q1 B）；继续删改 fork（R0 Q2 a）；单独起一个 Herdr 会话当后台（R1 Q1 a，绕开界面的输入记不到）；关掉应用即停 agent（R2 Q7 b）；切换只加日常派发离不开的功能（R6 Q25 b）。
