## What to build

来源：用户 2026-10-27：“还有判断人工介入那个,还是太频繁了,我按的键好像都会被记录,我之前看到好多什么输入空格键什么的,我建议是在我消息发送成功出去的那一刻,也就是输入完之后再记录,不然太乱了”。

现状：受管会话窗格（worker、审查员、执行主控）里，xterm 每送来一段数据（一个键、一段粘贴）后台就记一条用户输入，落在受管 attempt 上的同时派生一条 `human_intervention`。一句话打下来就是几十条，空格、退格各算一条。

做法（用户 2026-10-27 补充后定）：

用户补充：“我觉得这个判定是我输入的很简单,让 agent 通过我们的系统接口来沟通传递信息,我肯定是通过输入框发送的,这就能判定是我发的消息了,然后就是那个只记录我发送之后的完整消息,不要每次操作都要记录”。

- agent 只经 a2a 的接口（派发、收件箱、门禁回执）传话，所以窗格输入框里的输入就是用户的。
- 按键先攒成这个窗格的草稿，不记。按回车把它发出去时记一条：`form: message`，文字是攒下的整句（退格删掉的字不算，方向键、Home/End、Delete 按光标位置处理）。有方向键、Tab 这类编辑键时，在 `content.keys` 里列出；草稿跟不上的键（上下方向键翻历史、Tab 补全等）另标 `text_uncertain`。
- 只记发出的完整消息，操作不单独记：Esc、Ctrl-C、单按回车、鼠标上报都不记。Ctrl-C、Ctrl-D 清空草稿，被清掉的文字不记。
- 没发出去的草稿不记。终端原始字节照旧写进 `terminal_input_write_intent` 事件，不受影响；“紧急停止”指标照旧按写进终端的 Esc 计。
- 记录仍在回车写进终端之前完成；记录失败时，这个回车不写入（fail-closed 不变）。

## Acceptance

- [x] 修前版本经真实入口：在受管 worker 窗格里打一句带空格、退格的话再回车，记录是逐键的多条；修后只有一条，文字是发出的整句，人工介入也只有一条。
- [x] Esc、Ctrl-C 等操作不单独记；被 Ctrl-C 清掉、没按回车的草稿不记。
- [x] CLI 收到的字节不变。

通用：先在真实入口留红态再修根因；独立审查。
