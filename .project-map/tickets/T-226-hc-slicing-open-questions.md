## Question

T-224 盘点换运行时之前计划过的功能时，查到九处会改动已定规格或需要用户定方向（[报告](../../evidence/2026-10-31-batch29/T-224/REPORT.md) 第 6 节；Q9 旧测试处置见 T-225）。每项列研究建议：

1. **Q1 状态统一后是否保留“未知”。** hc 规格写“侧栏不再出现未知”，但 T-211 实测：程序没上报、Codex 登录页、core 崩溃后画面不完整时，hc 也给不出状态。
   - A 统一以 hc 为来源；没上报、失联、身份不明时仍显示未知，并说明原因。（建议）
   - B 暂不验收“不再出现未知”，先把四家的正常路径和失败路径做明确。
   - 两项都要改规格里那句绝对的话。
2. **Q2 hc 直接给主控终端写通知，与“输入都经后台”冲突。** T-211 已证实通知不经 attach，也不经收件箱。
   - A 允许 hc 直接写，但先证明来源能补记、能去重，不会误答草稿或权限框。
   - B 保留父子关系，关掉 hc 通知（`no_notify`），改由后台消费 hc 事件、经收件箱投递。（建议先用探针 P5 比较两者）
   - C 父子通知先不做，先做 T-216 的问题推送。
3. **Q3 core 崩溃后谁重启、丢了历史怎么显示。** 与 T-220 的结论一起定。
   - A 后台独占重启，画面不完整时明确提示，身份核对通过才继续。
   - B 允许客户端自行拉起，但须核对或拒绝被污染的环境。
   - C core 崩溃即暂停，由用户或执行主控核对后继续。
4. **Q4 要不要可直接写入的多窗口查看。**
   - A 写入一律经后台，多开的窗口只读（observe）。（建议）
   - B 多个窗口都可写，但都经后台登记；先定尺寸仲裁和记录方式。
   - C 允许外部直接 attach 写入；这样“所有用户输入都有记录”的承诺不再成立。
5. **Q5 心跳、超时换人、预算和更多自动化要不要进本批。**
   - A 本批只报 hc 已证实的 blocked、error、exit，现有截止时间不变。（建议）
   - B 另开决定票，先给出真实卡死场景、阈值和处置权限。
6. **Q6 指标是否改按 hc 的 turn 计。** T-211 已证实 Codex 启动时可能多计一个 turn。
   - A hc turn 单列为运行时序号，业务指标仍按原生回合和门禁事件。（建议）
   - B 另定义运行时活动指标并标明覆盖，旧指标保留原口径。
7. **Q7 是否重开旧 Enchanted 的分析类功能**（看清实际加载的指令、找重复问题、带引用的改进建议、脱敏）。
   - A 本批只打记录地基，以后再开。（建议）
   - B 先定隐私、来源和可外发范围，再切其中一项。
   - C 定完整范围后分票。
8. **Q8 agent 补全任务卡要不要界面入口。**
   - A 沿用主控在对话里补卡，不恢复已删的新建任务表单。（建议先确认这样是否已满足需要）
   - B 新做一个显式的“交给主控补卡”入口。
9. **Q10 一个任务能否跨多个仓库一起审查、一起集成。**
   - A 维持现状：主控协调多个任务，各自审查、各自集成。（建议）
   - B 另开决定票，定义跨仓库候选、失败与恢复。
