现象（2026-10-17 21:58，T-095、T-096 worker 启动，launch-b36694909e50444d902a951be715aa00、launch-0b12e76aae2640808eb9911b7c0266cb）：新 pane 里 oh-my-zsh 初始化时打印 '[oh-my-zsh] Would you like to update? [Y/n]'，然后等待读取输入。此时前台只剩 zsh 本身，T-094 的'前台连续 1500ms 只剩 shell'判据成立，Herdr 的 agent start 就把 codex 命令打了进去。首字母 c 被这个 [Y/n] 提示吃掉，oh-my-zsh 打印 'You can update manually'，判为不更新；剩下的 'odex …' 被当成命令执行，报 'command not found'。两次启动都以 timeout/unknown 失败，pane 保留为 wF:p66、wF:p67，Codex 没有起来，没有模型回合。

风险：如果启动命令的首字母是 y 或 Y、或者是回车，就会替用户应答 shell 初始化里的交互提问（这次是'是否更新 oh-my-zsh'），属于在用户环境里自动应答提示。这正是 T-094 Resolution 写明的局限（'初始化中途空闲超过窗口会误判'），而且实际后果比当时描述的更严重。

判断：'前台只剩 shell'不等于'shell 在等命令'——shell 在内置的 read 上等待交互输入时，前台同样只有 shell。需要一个能区分'提示符就绪'和'初始化中的交互读取'的机械信号，但不能往 pane 写探测命令（主控 T-094 已否决这种做法，因为会写进用户的 shell 历史）。可能的方向（待构思主控或用户裁定）：worker 的 pane 改用非交互、不加载用户 rc 的 shell（例如 zsh -f），或者用 Herdr 提供的命令型 pane 直接启动 codex，不经过用户的交互 shell。这会改变'窗格里跑用户的 zsh'这条约束（AGENTS 第三阶段），属于设计取舍。

标为 blocking，因为它会在用户环境里自动应答提示。修复方案定下来之前，执行主控会先在每次启动后核对 pane 回显，确认命令完整到达 codex。
