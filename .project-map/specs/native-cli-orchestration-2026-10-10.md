# Spec：原生 CLI 编排与 a2a 工作台（2026-10-10）

本 spec 是日期记录，综合 grilling 会话 [native-cli-orchestration](../../.grilling/native-cli-orchestration.md) 已确认的决定（用户 2026-10-10 回复"确认"），不提出新问题。之后的变更走新 ticket，不改写本文。每条决定的原话、来源，以及哪些是用户自己定的、哪些是采纳的推荐，见账本。

参考材料：立行《将军赶路不追小兔：多 Agent 调度体系的架构与实践》（2026-08-09，<https://zj1123581321.com/posts/260809-multi-agent-scheduling-architecture/>）及其附录 01–07。

## Problem

- 接 Synara 的统一层，几乎每张票都要改它的上游（provider 适配器、网关、投影）：T-055、T-058、T-061、T-064、T-066、T-068。
- 合并在门禁之外：日常派发里，worker 交付后由执行主控手工合进工作分支，冲突也由它手工解决；门禁自己的集成引用停在 T-046 那次。
- 提交看不出是谁、用什么干的：fork 上近期 52 个 a2a 提交作者都是 LuckyE，没有任务、会话、模型或思考强度。
- 没有验收打分、复盘与指标，"什么活派给谁"只能凭印象，系统自进化和以后的 Enchanted 没有数据可用。
- 很多规程只写在提示词里，长对话里容易丢。用户引用的文章原话："能用脚本保证的事情，就不要只靠提示词。"

## Solution

```text
工作台界面（Electron，借用 Synara 组件与样式）：项目 → 任务 → 会话窗格、面板、指标、设置
        │ 只是连接；关掉界面不影响后台
编排后台（常驻）：窗格托管（node-pty + zsh）、派发与唤醒、门禁、任务卡、收件箱、复盘调度、唯一 SQLite 库
        │ 启动参数、环境变量、钩子，只作用于各自会话
执行层：各家原生 CLI 的交互终端（第一版：Claude Code 跑主控，Codex 跑 worker 与 reviewer）
```

- agent 原样跑各家 CLI，a2a 只做编排、门禁与记录（T-069）。
- 能机械核对的由脚本和门禁保证，判断交给提示词和人（T-070）。
- 每次交付走同一串门禁检查；写和审是两个干净会话；集成直接落到项目工作分支（T-070）。
- 权限分四层，状态只认结构化信号，派发和唤醒写进窗格，数据只放一个库，问题上报与主控提问都上面板（T-071）。
- 提交带尾注可追溯，每个 attempt 结束打一次分，原始事件全记、指标现算，复盘手动或定期跑（T-072）。
- 构思主控与执行主控也作为窗格跑在工作台里；用户输入记录、两层主控、问题面板三项换到新载体（T-069）。

## 1. 组成

- **工作台**：本仓库的新目录（名称由第一个切片定，建议 `workbench/`），Electron 外壳加前端；从 fork 搬组件与样式，保留 MIT 版权声明。界面按"项目 → 任务 → 会话"展开，一个任务里有多个会话窗格。
- **编排后台**：常驻进程，脱离调用者的进程组（AGENTS.md 规则）；托管窗格、派发与唤醒、门禁、任务卡、收件箱、复盘调度；对外提供本地命令行，主控、worker、reviewer 与 `scripts/inbox` 都经它，界面也连它。运行时与 node-pty 一致（Node，推断）。
- **门禁核心**：从 fork 的 `packages/a2a-gates` 搬进编排后台，替换两处 Synara 依赖。搬完后它是唯一门禁入口，fork 里的门禁不再作入口，不保留两套路径；`acceptance/entry/a2a_gates.py` 改指新位置；交付 8 项、恢复 9 项、编排 18 项场景在新位置重新取得红态、绿态与反例。
- **数据**：编排后台的一个 SQLite 库，放工作台数据目录（内置盘，路径由第一个切片定）；轨迹归档也在这个目录。外置盘只放构建缓存，缺盘时构建报错，不回退（AGENTS.md）。

## 2. 任务卡

| 字段 | 谁填 | 说明 |
| --- | --- | --- |
| 编号 | 脚本 | ticket 号加序号，例如 ticket T-080 的第 1 张卡是 `T-080-1`；没有 ticket 的项目用项目短名加日期序号 |
| 来源 | 脚本 | ticket 与 `ready_rev`；没有 ticket 的项目可空 |
| 目标 | 执行主控 | 一两句，做完后用户或系统有什么变化 |
| 非目标 | 执行主控 | 至少一条 |
| 修改边界 | 执行主控 | "允许"必填，"禁止"可选；门禁按它检查交付 |
| 完成条件 | 执行主控 | 能跑的命令；至少一条在派发前由执行主控写好，不能只靠 worker 自己写的测试 |
| 红态命令 | 执行主控，可选 | 写了才查：候选里的新测试放到起点提交上必须失败，在候选上必须通过 |
| 任务类型 | 执行主控 | 后端逻辑、前端界面、缺陷修复、测试、重构、构建与基础设施、文档、调研；改词表要另做决定 |
| 修复对象 | 执行主控，缺陷修复类必填 | 原任务卡号或提交号，逃逸缺陷指标靠它算 |
| 复杂度 | 执行主控 | S、M、L |
| 执行器 | 执行主控 | CLI、模型、思考强度 |
| 起点、唯一写入者 | 脚本 | 起点是认领时工作分支的头；唯一写入者是本 attempt 的 worker 会话 |

- 用命令生成模板、校验（缺字段、完成条件不是命令就拒收），存进后台库；修改出新版本，门禁在任务注册时快照。
- 一张就绪 ticket 拆成一张或几张任务卡；任务卡全文随派发写进 worker 窗格，角色卡由同一命令附带。
- Herdr 期先用 markdown 模板（第 10 节）。

## 3. 一次交付怎么走

1. **认领**：建 attempt，建 worktree（第 4 节），记启动记录（第 5 节）。允许路径与活跃 attempt 有交集时默认拒绝派发，执行主控要并行须写理由，记下来。
2. **派发**：启动 worker 窗格，把角色卡和任务卡以 `⟦主控 #序号⟧` 标记写进窗格，记派发日志。
3. **交付**：同现有契约：身份、fence、spec 版本相符，候选是分配 worktree 的 HEAD 且工作区干净。
4. **机械检查**：在工作分支当前头 G 上合并候选得 M，依次查路径边界、完成条件命令、红态（卡上写了才查）、规则式检查（项目配置的 lint、类型检查等）、提交尾注（第 8 节）。任一不过就打回：失败摘要以 `⟦门禁 #序号⟧` 写回 worker 窗格，worker 改完重交，整串重跑；同一 attempt 连续 3 次打回，停止自动回写，交执行主控。文本冲突按第 4 节处理。
5. **独立审查**：机械检查全过后，后台新开一个 reviewer 会话（只读启动参数，不续接任何会话），附任务卡、候选的改动和上一轮问题清单（若有）。结论"可合并"或"需修复"加问题清单（位置、失败场景、建议），绑定候选提交号写回门禁。门禁核对审查会话不是本任务的写入会话、是为本次审查新开的；"需修复"时清单写回 worker。
6. **验收与打分**：执行主控用集成命令验收，打分作为参数一起给（第 8 节），缺了拒收。
7. **集成**：CAS 把工作分支从 G 推进到 M，不 push。分支被某个工作区检出时，在那个工作区里快进；会覆盖未提交改动时拒绝并上报，不 stash、不 reset。CAS 落空（分支已变）时自动重新验收：机械检查在新的 M 上重跑；审查结论绑定候选提交号，候选不变时沿用。连续重新验收超过上限（默认 3 次）交执行主控并上报（风险 R8）。
8. **结束**：回收窗格（核对身份，已 idle 且交付已提交），按第 4 节清理 worktree。不做了的用放弃命令结束 attempt，带结果与理由。

锁、fence、CAS、attempt 绑定与中断恢复的语义不变。冻结契约这次的改动（均经用户同意，见 T-070）：路径检查；验收扩成检查串；清理干净的 worktree，取代"保留所有 worktree"；核对提交尾注；缺打分拒收；集成目标改为项目工作分支，取代"不更新任何用户工作分支"。

## 4. worktree 与冲突

- **命名**：目录 `<项目>/<任务卡号>-a<序号>`，分支 `a2a/<任务卡号>-a<序号>`，例如 `T-080-1-a2`；验收与审查用的 worktree 在其后加用途与序号，detached。
- **清理**：

| attempt 结局 | 工作区 | 处理 |
| --- | --- | --- |
| 已集成 | 干净 | 删目录与分支名；提交留隐藏引用 `refs/a2a/attempts/<任务卡号>/a<序号>`；事件与历史全留 |
| 打回、撤销、放弃 | 干净 | 留隐藏引用，删目录 |
| 任何结局 | 有未提交改动或状态未知 | 不删，上报到面板 |
| 验收、审查用的 | — | 结果存库后删 |

- **冲突**：验收时合并出现文本冲突，门禁自动把冲突信息写回 worker：基于工作分支最新的头重新整理、解决冲突、重跑完成条件后重交，整串门禁连审查重跑；worker 会话已结束则开新 attempt。程序不替用户在两边改动之间取舍。

## 5. 会话：启动、权限与环境

- **启动记录**：CLI 与版本、模型、思考强度、角色、完整 argv、Claude 的 `--settings` 内容或 Codex 的 `-c` 覆盖项、角色卡版本、项目在启动时的提交号、worktree、任务与 attempt。存进库，记录号写进环境与尾注。
- **权限四层**（T-071）：角色卡；任务卡路径加门禁检查；每会话启动参数（例如 reviewer 的 Codex 只读沙箱、Claude 的权限模式与工具白名单）；收件箱命令行按角色限定能写的条目。设置页"角色权限"编辑启动参数与路径规则。
- **环境变量**：项目、任务、attempt、会话、角色、启动记录号，加上为本会话 git 指定钩子目录的 `GIT_CONFIG_*` 三项。
- **Claude Code**：启动时用 `--session-id` 指定原生会话号，带 `--model`、`--effort`、`--settings`（hooks 只经这里传入）。**Codex**：带 `-m`、`-c` 指定思考强度与 `notify`，按角色给沙箱与审批参数。
- 不写 `~/.claude`、`~/.codex` 等全局配置。
- 会话在窗格的 zsh 里启动；CLI 退出后 shell 还在。

## 6. 状态、派发、唤醒与用户输入

- **状态**：只认结构化信号（Claude Code 的 hooks 与 OSC 7501，Codex 的 `notify`），拿不到的显示"未知"，不用正则读屏或标题。
- **派发与唤醒**：派发文本以 `⟦主控 #序号⟧` 写进窗格；门禁回写用 `⟦门禁 #序号⟧`；两个主控互相唤醒，往对方窗格写带标记的提示；收件箱条目仍是事实来源。
- **用户输入**：用户在窗格里亲手打的字记为用户输入（T-050 的语义）；落进受管 worker 窗格的记为人工介入。注入的文字在写入前登记，记录器跳过已登记的部分，不当作用户输入。
- 第一个切片先验证 Codex 的"等确认"信号（R6）与两家窗格注入的稳定性（R7），不通过就停下报告，不改用读屏。
- **批准与派发分开**（2026-10-10 用户决定，依据 T-074 实测：Codex 等批准时注入的文字被当作同意）：受管 worker 以"不问"的审批模式启动（Codex `approval_policy=never`、Claude `--permission-mode dontAsk`），越界操作被拒并由 worker 上报，窗格里没有批准窗口；主控窗格保留批准，只在空闲时注入：最近一条结构化事件是"回合结束"且其后没有"回合开始"时才写，其余时间排队（2026-10-11 用户决定；权限请求 hook 没有结束事件与请求标识，不能作恢复依据，见 T-074）。注入方法用 bracketed paste 后单独回车。

## 7. 面板

- 同一个面板收两类条目：worker、reviewer、monitor 的**问题上报**（语义同 controller-split spec 第 4 节，处置规则不变）；构思主控的**主控提问**。
- 主控提问由构思主控用命令放上面板，每题带类型、选项、推荐和依据。
- 用户逐题点选、采纳推荐或写几句，草稿自动保存；可逐个或打包发送，已答两题以上默认打包，格式"问题 N：…… / 用户答复：……"；答复写进提问方的窗格，每条记为 `answer` 用户输入并指向问题。
- 执行主控的 needs-decision 由构思主控改写后放上面板；用户在对话里答的，面板标"已在对话中答复"。
- 系统通知：新的"等你决定"、blocking、完成报告、BLOCKED/NO_GO 时发；通知读取失败不能悄悄停掉（原 T-057、T-067 的要求）。

## 8. 追溯、打分、复盘与指标

**提交尾注**：`A2A-Task`、`A2A-Attempt`、`A2A-Session`、`A2A-Role`、`A2A-Tool`（CLI 与版本）、`A2A-Model`、`A2A-Effort`、`A2A-Native-Session`、`A2A-Launch`。提交时的模型取该会话最近一轮的记录，拿不到写 `unknown`。门禁核对规则见 T-072；没有尾注的提交记为用户本人提交与人工介入，标"推断：缺尾注"。

**验收打分**：每个 attempt 结束时一条，是集成或放弃命令的参数。

| 字段 | 谁填 |
| --- | --- |
| 时间、任务卡、项目、CLI、模型、强度、任务类型、复杂度、交付轮数、耗时、人工介入次数、各项检查的打回次数 | 脚本 |
| 结果：通过、升级（换更强的执行器重做）、放弃（只记理由，不打分） | 执行主控 |
| 边界纪律 0–3（3 严守边界，0 大面积自作主张）加理由 | 执行主控 |
| 工程品味 0–3（3 拿来即用，0 看着就想重写）加理由 | 执行主控 |
| 备注 | 执行主控 |
| 用户自己的分 | 用户，另存一条，不覆盖 |

**复盘**：

- 启动：手动"立即复盘"，或按周期（默认每周一 9:00，可改可关）。
- 执行：每次选 CLI、模型、思考强度，默认 Claude Code、Opus 5.5、medium；在普通窗格里跑，本身也是受记录的会话。
- 复盘包由脚本备好：时间范围（默认从上次复盘到现在）内的任务、门禁逐项结果与打回原因、审查结论、打分、问题上报、用户输入与介入、面板问答、提交尾注汇总、指标快照、原生会话记录的路径。
- 权限：只读代码和数据，只写自己的报告。
- 产出：中文报告存项目的 `findings/`（没有这个目录的项目存工作台数据目录）；改进建议逐条放上面板，用户批了，构思主控才写成 ticket 或改角色卡。
- 轨迹归档：后台把它启动的每个会话的原生记录增量复制、压缩，存在工作台数据目录，不进 Git，设置页显示占用空间。

**原始事件**（从第一个切片起全记，只追加）：会话启动记录；回合开始与结束、权限等待；用户输入与人工介入；派发记录；门禁每一项检查的结果；每次交付的改动行数与文件数；审查结论与问题清单；打分；问题上报与面板问答的时间；worktree 的创建、清理与残留；提交尾注；复盘记录。

**指标**：都从原始事件现算，不单独存计数。第一版四个视图：

1. 模型使用分类：项目 → 任务 → 会话的角色、CLI、模型、强度，按模型与任务类型汇总。
2. 一次到位率与打回原因：第一次交付就过完整门禁、全程没人介入的比例；打回按检查项分类。
3. 用户的注意力消耗：每集成一个任务，用户答题、审批、介入、叫停的次数。
4. 打分汇总：执行器 × 任务类型。

以后按需加的视图（不用改采集）：最长自主运行时长、推荐采纳率与答复等待、权限等待、审查命中与漏检、逃逸缺陷、任务卡质量、上下文与换会话、规则版本对照、编排层自身（派发送达率、"未知"占比、后台重启与恢复、残留 worktree）。看板上的变化只算观察，收益主张仍需对照实验（AGENTS.md）。

## 9. 数据

## 10. Herdr 期与切换

- **切换前**：日常派发仍经 Herdr；收件箱文件、`scripts/dispatch`、`scripts/session-copy` 照旧。
- **Herdr 期先用三样**（T-072）：
  - 任务卡 markdown 模板：执行主控写给 worker 的说明按第 2 节的字段写，brief 改叫任务卡。
  - 提交尾注：`scripts/dispatch` 启动 worker 时带第 5 节的环境变量与钩子目录。
  - 验收打分：执行主控验收时顺手写一行到追加式文件；执行主控角色卡加一句"验收时顺手打分"。

## Test seam

- 最高的检查面：编排后台的命令行入口（主控与 worker 用的同一个），驱动真实窗格里的真实 Codex worker，对夹具仓库走完整门禁。证据：命令与输出、库里的事件读回、Git 引用读回；界面用 Electron 截图或录屏取证。
- 真实 Codex 验收按 AGENTS.md 使用隔离的 `CODEX_HOME`，最少 turn。
- 每个切片保留端到端的产物和重新生成它的命令。
- 构思主控切 S1 时与用户确认这一检查面。
