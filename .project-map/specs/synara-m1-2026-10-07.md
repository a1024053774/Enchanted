# Spec：基于 Synara 的 M1（2026-10-07）

本 spec 是日期记录，承接 [intent.md](../../intent.md) 的 M1。之后的变更走新 ticket，不改写本文。被取代的 GPUI/Muster 方案见 [workbench-m1](workbench-m1-2026-10-06.md)。

## 问题

从零自建的 GPUI 界面观感不可接受，自建成本过高；a2a 门禁（`coop.py`）只能经终端读屏判断 agent 状态，运行时绑定在 Herdr 或 Muster 上。用户要在一个现代应用里按"项目 → 任务 → agent"组织多 agent 分工，并让门禁成为这个应用的原生部分。

## 方案

在 Synara 的 fork（`a1024053774/synara`，分支 `a2a`，起点 v1.0.1-beta.2）上：

- 用户在 Synara 里打开一个项目，项目下有多个任务；每个任务是一个任务窗口，里面有多个 agent 会话分工（例如一个 worker、一个 reviewer）。
- 任务可以挂上验收合同，成为受管任务。受管任务的派发、交付、验收、集成和回收都走 a2a 门禁；门禁状态显示在任务窗口上。
- worker 是 Synara 经原生协议启动的 agent 会话（M1 以 Codex app-server 为准）。worker 写完代码、在自己的 worktree 提交后，通过门禁提供的工具显式交付；独立 oracle 验收通过后，门禁用 CAS 写入集成引用。
- 主控可以是用户在界面上操作，也可以是一个 agent 会话经门禁工具操作；两者调用同一个门禁核心。

## 已核实的 Synara 事实（2026-10-07，本地克隆 `f176e89`）

- 单仓：`apps/{desktop,server,web,marketing}`、`packages/{contracts,shared}`；Bun + Turbo；服务端用 Effect 与 SQLite（`@effect/sql-sqlite-bun`）。
- agent 经 Codex app-server（`codexAppServerManager`）、Claude Agent SDK、ACP、OpenCode SDK 运行；另有 node-pty 终端。
- 服务端有面向 agent 的控制网关（`packages/contracts/src/agentGateway.ts`，经 MCP 暴露）：能力含 threadRead、threadCreate、threadWait、automations；创建 thread 时可指定 prompt、projectId、`environment`（local / worktree）、baseRef、baseBranch、branchName、`runtimeMode`（approval-required / full-access）、notifyCreatorOnComplete；单次最多 20 个 thread，等待上限 60 秒，带幂等请求 ID 与"每个活跃 turn 一个创建计划"。
- 界面已有 split views、thread goals、Automations、Studio、worktree checkout。

## 设计要点

### fork 与上游

- `main` 只镜像上游；我们的工作在 `a2a` 分支。定期把 `upstream/main` merge 进 `a2a`（与 Synara 作者自己的做法一致，不 rebase 已发布分支），每次合并保存冲突清单与测试结果。
- 我们的代码集中在：新 workspace package `packages/a2a-gates`（门禁核心），`apps/server` 中少量接入（注册服务、MCP 工具、对外入口），`apps/web` 中独立目录（任务窗口与门禁状态组件）。对上游文件的改动列清单，尽量只做注册与挂载。
- 通用修复以独立提交方式整理，便于给上游提 PR。

### 构建与缓存

- checkout 在内置盘 `~/Documents/Code/synara`；`node_modules` 在 checkout 内。
- Bun 全局缓存、Electron 及其二进制下载缓存指向 `/Volumes/WD-Elements/dev-cache/synara/`；由一个入口脚本在安装、构建前检查外置盘挂载，缺盘即报错，不回退。具体环境变量以 Bun、Electron 当前文档为准，在第一张 ticket 中核实。
- 记录内置盘占用、安装耗时、dev server 与桌面版启动耗时。

### 隔离运行

- 开发与验收使用独立的 Synara 数据目录与身份（参照其已有的 desktop identity 机制），不读写用户可能已安装的 Synara 数据；真实 Codex 验收沿用 AGENTS.md 中隔离 `CODEX_HOME` 的规则。

### 层级模型

- 项目 = Synara 项目。任务 = 一组 agent 会话加上可选的验收合同。agent 会话 = Synara thread。
- 第一步核实 Synara 是否已有"一组 thread"的持久分组（例如创建者与被创建 thread 的关系）；若没有，在 `packages/a2a-gates` 中保存任务与 thread 的归属，并在 web 中提供任务窗口（把同一任务的 thread 并排或分栏显示）。不修改上游 thread 的数据结构。

### 门禁

- **契约**：照搬 [受管交付](managed-delivery-2026-10-06.md)、[恢复](recovery-2026-10-06.md)、[自动运行](supervised-run-2026-10-06.md) 三份规格中与运行时无关的语义：task 冻结输入、attempt/session/fence/spec_rev 身份、submit 校验、独立 oracle 在 detached worktree 中执行、`git update-ref` CAS 集成、操作锁、中断恢复与 `needs_reconciliation`。
- **唯一核心、多个传输**：所有状态变更只在 `packages/a2a-gates` 的一个核心模块里发生，持操作锁。对外提供：
  1. CLI 入口，命令与 JSON 输出（`ok`、`error` 码、退出码 0/1/2）对与运行时无关的命令保持 `coop.py` 的契约，使现有交付与恢复验收脚本可以只换入口重跑；
  2. MCP 工具，供 agent 会话调用（例如 worker 的 `a2a_submit`，主控的派发与查询）；
  3. 服务端内部调用，供 web 界面使用。
  三者都调用同一核心；界面与 agent 不能绕过它直接写状态。
- **派发与回收**：派发时经 Synara 内部服务创建 worker thread（worktree 环境、baseRef 为集成头、明确的模型与参数），把 attempt 身份与交付方式写进任务说明；回收时停止并归档该 thread。运行时身份改为核对 thread、turn 与 worktree，不再依赖终端进程组。
- **交付信号**：worker 显式调用 `a2a_submit` 工具提交 attempt 身份与完整提交号；thread 结束、空闲或模型自述都不推进业务状态。
- **存储**：门禁使用自己的 SQLite 文件（位于 Synara 数据目录下），追加式事件表，不与 Synara 的表混写。

### 界面

- 任务窗口显示门禁状态（claimed、submitted、verified、accepted 及失败原因）；界面对受管任务的操作只调用门禁核心。
- 在受管 worker 会话里由人直接输入，记为人工介入事件。
- 视觉沿用 Synara 自身的主题与组件，不另起一套样式。

### 切换

- M1 第 1～5 项通过后，主控与 worker 的日常分派改到 Synara；删除 a2a 仓库中 Muster 引擎与 `coop.py` 的运行路径（参考实现保留在 git 历史与证据中），不保留两套路径。

## 验证接缝（待用户确认）

1. **门禁**：在隔离数据目录中运行真实的 Synara 服务端，以门禁 CLI 入口为程序可核对的接缝；交付 8、恢复 9 项沿用现有脚本，只替换入口；编排 18 项按新运行时改写其边界替身，并标明是隔离证据。每套都要有红态、绿态与反例。
2. **真实闭环**：真实 Codex（经 app-server）在 Synara thread 中完成分页夹具，经 `a2a_submit`、独立 oracle、CAS 集成与回收；追加式运行记录。
3. **界面**：桌面版的截图或录屏，展示"项目 → 任务 → 多个 agent 会话"与门禁状态；外观由用户判断。

所有验收不读写用户正在使用的 Herdr、Codex 配置与可能已安装的 Synara 数据。
