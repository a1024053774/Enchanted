# 主控决定 01：有界计时方法

目标：定位原有 2 秒并发忙拒绝失败，区分入口启动与门禁锁判定。非目标：修复 fork、改变验收、提高时限、重新发布或真实模型调用。本轮完成诊断后交主控选择修正方向。原 INCOMPLETE 与独立审查 FAIL 保留。

已观察：fork 当前为 `c426a5f939e26a69606616cc88df59cd898efe25`，其门禁、CLI、构建入口与失败时 `d3b5bcc` 原字节一致，B 部分只改变桌面启动代码。原失败发生于真实 CLI、真实门禁锁和原 2 秒忙拒绝条件。冷启动假设来自主控决定，尚未证实。

用新的 /tmp 隔离夹具，从原生真实 `verify` 启动并等待原分页 oracle 的外部屏障。该进程保持真实任务操作锁。另起原入口 Python CLI，交替发送 verify/integrate，预期均为 exit 1 与 `operation_busy`。owner、oracle、task、attempt、Git、SQLite 和信号记录沿用现有夹具；不直接写产品业务状态，不替换门禁或锁。

两种条件每个命令各 20 次（共 80 次分段样本），每次分段样本配一个无钩子原入口对照，以显示观察开销与行为是否保持。空闲条件指不启动本探针 CPU 负载；系统实际 CPU、内存和已有负载保留，不停止其他任务，也不声称整机没有其他活动。负载条件启动本探针持有的 10 个 `yes` 子进程，标准输出到 `/dev/null`，分别记 PID、argv、启动与停止；只停止本探针创建的进程。

观察通过环境启用：Python `PYTHONPATH` 只加入本目录 `hooks/` 的 sitecustomize；Bun `BUN_OPTIONS=--preload .../bun-timing.cjs`。首次试运行发现 Python 3.9 的 `monotonic_ns()` 与本机 Bun 的 `hrtime.bigint()` 为进程相对值，无法跨 exec 相减；原失败保存在 `hook-pilot.json`、`hook-pilot.jsonl` 与 `clock-calibration-01.json`，没有用于正式阶段统计。改为所有进程统一调用 macOS `clock_gettime(CLOCK_MONOTONIC_RAW)`：Python 用现有标准库，Bun 用内建 FFI 调用系统 libSystem；新试运行须确认所有标记都在同一外部区间内。

Bun preload 的支持来自 [官方环境变量说明](https://bun.com/docs/runtime/environment-variables) 与 [运行参数](https://bun.com/docs/runtime)，FFI 来自 [官方说明](https://bun.com/docs/runtime/ffi)。未新增依赖。fork 磁盘文件不改、不在内存重写源文件。

钩子只围绕现有 parseArgs、DatabaseSync 构造/exec 和 stdout.write 记录单调时间；原参数、返回值、回调与异常继续交给原函数。事件分段覆盖：父进程启动→Python entry；entry→exec；第二 Python 构建入口→exec Bun；Bun 引导和钩子初始化；TS 模块加载/参数解析；state 打开/初始化；任务锁打开、非等待 BEGIN IMMEDIATE 判定；拒绝输出和退出。钩子写入也有代价，无钩子对照不能给每次分段减去一个假定常数。

先做一组外部观察试运行。若时间域不一致、关键钩子未覆盖、结果不再 operation_busy、owner 不再活跃或必须改 fork 才能分段，就保留现场并停止，不制造阶段值。每个 child 最长观察 10 秒，超过 2 秒照原期限计为超时，不以诊断观察上限代替断言；只针对已核对的本次 CLI 终止。每批最多 5 组，oracle owner 的原 60 秒期限保持；必要时在期限内收尾后为下一批创建新的原生 owner。全轮最多 600 秒，CPU 负载仅在负载阶段存在。

Tracer bullet：先用一组真实 Python → Bun → TS → SQLite 锁 → JSON 拒绝记录验证分段，再扩为 20 次。Deep modules：生产核心不拆分，诊断仅观察现有调用。Ubiquitous language：沿用 task、attempt、session_id、fence、spec_rev 和操作锁。
