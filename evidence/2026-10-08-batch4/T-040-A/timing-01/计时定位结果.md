## 计时有效性与已知限制

首次试运行发现本机 Python 3.9 的 `monotonic_ns()` 和 Bun 的 `hrtime.bigint()` 是进程相对时间，跨 exec 拼接出现负值。原始失败、返回的真实拒绝与校准记录在 `hook-pilot.json`、`hook-pilot.jsonl`、`clock-calibration-01.json`，没有被覆盖或计入统计。

第二先导和正式观测统一使用 macOS `clock_gettime(CLOCK_MONOTONIC_RAW)`：Python 标准库和 Bun 内建 FFI 调用同一系统时钟。所有正式事件都落在外部起止区间，阶段单调且没有缺段。`hook-pilot-02.json` 保存新时钟的先导验证。观察钩子通过 `PYTHONPATH` 与 `BUN_OPTIONS --preload` 启用，没有改磁盘上的 fork 或在内存重写源文件；仅包装原 parseArgs、DatabaseSync、exec 和 stdout 以记录事件，继续传递原参数、返回、异常和回调。Bun preload 的支持见 [官方环境变量](https://bun.com/docs/runtime/environment-variables)，FFI 的调用方式见 [官方 FFI 文档](https://bun.com/docs/runtime/ffi)。FFI 只用于此次观察，不进入产品。

不能用配对响应相同证明钩子对产品所有路径完全无影响；本轮仅核对真实忙拒绝、原 owner 的完成、Git 不变和没有第二 oracle。参数解析段只覆盖 Node util.parseArgs；完整请求构造、Schema 校验、SQLite 初始化按表中其他阶段报告，不混称为解析时间。Bun 引导段包含首次 marker 前的观察库加载，退出段包含日志落盘和父进程回读，不冒称为纯产品耗时。

收尾的版本采集工具在首轮 10.002 秒时仍在运行，最终退出 0；该顺序命令未采集每个子命令时间，不能判断延迟位于 Python、Git、fork 入口还是其他环节。记录见 `runtime-version-observation.json`，不计入 160 个忙拒绝样本，不冒称为原故障的复现。

本轮 CPU 条件确实区分，且锁失败即时返回。本轮没有复现原现场的页面回收、磁盘 I/O、转译缓存失效或并行构建内存压力；没有足够证据选定原失败原因，不能推出原 2 秒断言已经稳定。

## 结论与最小选项，交主控决定

**measured**：当前样本中的锁 BEGIN IMMEDIATE 忙判定最大 0.185 毫秒，返回实际 SQLite locked 错误；没有等待锁或接近 2 秒的证据。state 打开/初始化也未接近 2 秒。TS 模块图加载与两段 Python 启动/入口检查占主要时间，CPU 饱和使其增大，但总时间仍不到 342 毫秒。

**inferred**：CLI 启动链是当前可见的主要延迟成本。这个事实支持把未来超时定位标记放在启动链上；它不证明原来的两次超时就在 TS 加载，更不证明 CPU 单独导致原故障。

**unknown**：原两个进程被夹具在 2 秒后终止，没有当时的阶段标记。原失败的精确卡点及其触发条件仍未知。
