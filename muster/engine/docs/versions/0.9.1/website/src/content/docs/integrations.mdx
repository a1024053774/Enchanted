Muster detects supported agents automatically. Install official integrations when you want native agent session restore, direct lifecycle reports, or both. See [Agents](/docs/agents/) for the full status authority model.

## Install integrations

Open settings inside Muster and use the integrations tab to install recommended integrations for agents found on your `PATH`, or run commands manually:

```bash
muster integration install pi
muster integration install omp
muster integration install claude
muster integration install codex
muster integration install copilot
muster integration install devin
muster integration install droid
muster integration install kimi
muster integration install opencode
muster integration install kilo
muster integration install hermes
muster integration install qodercli
muster integration install qwen
muster integration install letta
muster integration install cursor
muster integration install mastracode
muster integration install antigravity-cli
muster integration install grok
```


Muster saves integration configs atomically on Linux/macOS and for new files; existing Windows files keep their permissions through a backup-first, in-place update. If Windows reports a backup, close the agent and inspect the config before retrying: discard—not restore—an unfinished `.muster-backup.pending` only after verifying the config, or restore completed `.muster-backup` contents into the existing file if needed (if missing, establish its intended permissions first), then verify the config and remove the backup.

## How Muster uses integrations

Muster uses integrations in two ways:

| Integration type | Agents | Effect |
| --- | --- | --- |
| Lifecycle authority | Pi, OMP, Kimi Code CLI, OpenCode, Kilo Code CLI, MastraCode | When installed and actively reporting for the pane, hook or plugin events author `idle`, `working`, and `blocked`. Muster does not also use screen manifest fallback for that same lifecycle authority. |
| Session identity | Claude Code, Codex, GitHub Copilot CLI, Devin CLI, Droid, Qoder CLI, Qwen Code, Letta Code, Cursor Agent CLI, Hermes Agent, Antigravity CLI, Grok CLI | The integration reports native session references for restore. State still comes from Muster's screen manifest detection. |

Custom integrations can also report state that is not visible in the native terminal UI. They do not need to be built into Muster or use a recognized agent executable.

## Integrate your own agent

An agent running in a Muster pane inherits `MUSTER_ENV`, `MUSTER_PANE_ID`, `MUSTER_BIN_PATH`, and `MUSTER_SOCKET_PATH`. If the agent exposes lifecycle hooks, use those hooks to report semantic state through Muster's CLI:

```bash
"$MUSTER_BIN_PATH" pane report-agent "$MUSTER_PANE_ID" \
  --source custom:my-agent \
  --agent my-agent \
  --state working
```

Report `idle` when the agent is ready for input and `blocked` when it needs a user decision. Use `--message` to describe a block. When the agent exits, release the same source's lifecycle authority:

```bash
"$MUSTER_BIN_PATH" pane release-agent "$MUSTER_PANE_ID" \
  --source custom:my-agent \
  --agent my-agent
```

Report only when `MUSTER_ENV=1` and the required variables are present. This keeps the integration a no-op outside Muster. Keep `--source` stable and unique to the integration. If reports can arrive out of order, include a strictly increasing `--seq`; Muster ignores stale sequence numbers from the same source.

You can include `--agent-session-id` or `--agent-session-path` with `report-agent`, or use `pane report-agent-session` when session identity changes independently of state. Muster exposes that reference through its pane and agent APIs. Automatic session restore also requires Muster to know how to launch that agent and resume the referenced session.

Use `MUSTER_BIN_PATH` and the CLI wrappers for portable integrations. Code that needs direct IPC can send the equivalent `pane.report_agent`, `pane.report_agent_session`, and `pane.release_agent` requests described in the [Socket API](/docs/socket-api/#agent-state-reporting).

[Prime Agent's built-in Muster reporter](https://github.com/PrimeIntellect-ai/prime-agent/blob/main/packages/coding-agent/src/core/extensions/builtin/muster-agent-state.ts) is a real-world example. It activates only inside Muster, maps agent events to `working`, `idle`, and `blocked`, preserves report ordering across sessions, and releases authority on exit.

Some integrations report native agent session references. Muster uses official session references to resume Claude Code, Codex, Devin CLI, Droid, Kimi Code CLI, Qoder CLI, Qwen Code, Letta Code, Cursor Agent CLI, Grok CLI, GitHub Copilot CLI, Pi, OMP, Hermes Agent, OpenCode, Kilo Code CLI, MastraCode, and Antigravity CLI panes after a Muster server restart unless `[session] resume_agents_on_restore = false` disables it.

Native session restore requires current Muster integrations: Pi integration version `2`, OMP version `3`, Claude Code version `6`, Codex version `5`, GitHub Copilot CLI version `2`, Devin CLI version `2`, Droid version `2`, Kimi Code CLI version `3`, Qoder CLI version `2`, Qwen Code version `1`, Letta Code version `1`, Cursor Agent CLI version `1`, Grok CLI version `2`, OpenCode version `5`, Kilo Code CLI version `1`, Hermes Agent version `5`, MastraCode version `1`, or Antigravity CLI version `1`. Check installed versions with `muster integration status`.

## Pi

Install the Pi integration:

```bash
muster integration install pi
```

Muster writes the bundled extension to:

```text
~/.pi/agent/extensions/muster-agent-state.ts
```

If `PI_CODING_AGENT_DIR` is set, Muster writes to `$PI_CODING_AGENT_DIR/extensions/muster-agent-state.ts` instead. Muster creates the extensions directory when the Pi agent directory already exists. Uninstall removes only that extension file.

## OMP

Install the OMP integration:

```bash
muster integration install omp
```

Muster writes the bundled extension to:

```text
~/.omp/agent/extensions/muster-omp-agent-state.ts
```

Muster uses `PI_CODING_AGENT_DIR` as the complete agent directory when set. Otherwise, it uses `$HOME/$PI_CONFIG_DIR/agent` when `PI_CONFIG_DIR` is set, falling back to `~/.omp/agent`. If Pi and OMP resolve to the same extension directory, Muster refuses the OMP install so the OMP extension cannot be loaded by Pi. Configure separate agent directories before installing both integrations. Muster creates the extensions directory when the resolved OMP agent directory already exists. Uninstall removes only that extension file.

The OMP integration reports `omp` as the agent label, lifecycle state, and native session identity through Muster's socket API. It does not require native process detection for the `omp` executable, and Muster can resume an OMP pane with `omp --resume=<session>` after a server restart.

## Claude Code

Install the Claude Code hook:

```bash
muster integration install claude
```

The hook reports Claude Code session identity to the local Muster socket on session start. Claude Code state comes from Muster's screen manifest detection.

Claude integration v10 matches only the documented `SessionStart` sources: `startup`, `resume`, `clear`, `compact`, and `fork`. This prevents Grok's `new` and `load` events from launching the imported Muster Claude hook, without disabling unrelated Claude-compatible hooks. Reinstall the Claude integration after upgrading to migrate the previous wildcard matcher. New Claude source values require an integration update.

Muster uses `~/.claude` by default, or `CLAUDE_CONFIG_DIR` when set. The Claude config directory must already exist. Install writes `hooks/muster-agent-state.sh` and updates `settings.json` with Muster hook entries. Uninstall removes the matching hook entries and deletes the hook script.

## Devin CLI

Install the Devin CLI hook:

```bash
muster integration install devin
```

The hook reports native session identity from Devin session, prompt, tool-use, permission, and stop events. Devin state still comes from Muster's screen manifest and OSC detection because Devin hooks do not emit a reliable state transition after every permission cancellation or user interrupt.

Muster uses `$XDG_CONFIG_HOME/devin` when `XDG_CONFIG_HOME` is set. Otherwise, it uses `~/.config/devin` on Linux and macOS or `%APPDATA%\devin` on Windows. The Devin config directory must already exist. Install writes `muster-agent-state.sh` on Unix or `muster-agent-state.ps1` on Windows and updates `config.json` with Muster hook entries. The hook refreshes the session reference while Devin runs. Uninstall removes Muster entries from `config.json` and deletes the hook script.

Muster resumes stored Devin sessions with `devin --resume <id>`. Native screen manifest detection remains the state authority whether or not the hook is installed.

## OpenCode

Install the OpenCode plugin:

```bash
muster integration install opencode
```

The integration supports OpenCode V1 `1.18.29` or later and OpenCode V2 (tested with beta `19242`). The OpenCode config directory must already exist. Muster installs the server entrypoint at `~/.config/opencode/plugins/muster-agent-state.js`, the shared TUI plugin at `muster-tui-session.js`, and a V2 TUI entrypoint at `muster-opencode/tui.js` in that config directory.

Install registers the V1 TUI plugin in `tui.jsonc` and the V2 TUI plugin in `cli.json`, preserving other preferences and plugins. If OpenCode still has V1 TUI preferences to import (`tui.json` or `kv.json`), Muster defers registration so the first-start migration can run; start `opencode2` once and reinstall the integration afterward. Otherwise Muster creates `cli.json` with the plugin registration. Restart the OpenCode TUI after installation. Uninstall removes the managed plugin files and their configuration entries.

V2 lifecycle reporting runs in the pane-local TUI, which associates events with its selected root session even when multiple panes share one OpenCode server. Completion and interruption clear the working state; pending permission requests, pending forms, and failed executions keep the pane blocked. V2 Mini and headless clients do not run the TUI plugin and therefore do not provide this lifecycle reporting.

The plugin reports lifecycle state and session identity while OpenCode runs inside a Muster pane. After OpenCode emits a session-bearing event, Muster can use the reported session id to resume the pane with `opencode --session <id>`. Native screen manifest detection remains available when the plugin is not installed.

## Hermes Agent

Install the Hermes Agent plugin:

```bash
muster integration install hermes
```

Muster writes `plugins/muster-agent-state/` under the Hermes home directory and enables `muster-agent-state` in its `config.yaml`. `HERMES_HOME` defaults to `~/.hermes` on Unix and `%LOCALAPPDATA%\hermes` on Windows. The Hermes config directory must already exist. Restart Hermes after installing so the plugin loads. Uninstall removes the plugin directory and removes `muster-agent-state` from `plugins.enabled`.

The plugin reports the resumable session id while Hermes runs inside a Muster pane. Muster uses screen manifest detection for `working`, `idle`, and `blocked`, and can use the reported session id to resume the pane with `hermes --resume <id>`.

## Letta Code

Letta Code integration installation is experimental and CLI-only. It is not listed in the Settings integration screen or the JSON integration API. `muster integration status` reports it as `letta (experimental)`. Agent detection and `muster agent start --kind letta` are supported independently of this installation restriction.

Install the Letta Code hook:

```bash
muster integration install letta
```

The quiet `SessionStart` hook reports the conversation ID for native restore. Letta Code state still comes from Muster's screen manifest detection.

Muster uses `~/.letta`. The config directory must already exist. Install writes `hooks/muster-agent-session.sh` (`hooks/muster-agent-session.ps1` on Windows) and adds a Muster entry to `settings.json`. Uninstall removes only the matching entry and managed script.

Muster resumes named conversations with `letta --conversation <id>`. It records the default conversation as `default:<agent-id>` and resumes it with `letta --conversation default --agent <agent-id>`.

## Antigravity CLI

Install the Antigravity CLI hook:

```bash
muster integration install antigravity-cli
```

Muster uses `~/.gemini/config/` by default, or `ANTIGRAVITY_CLI_CONFIG_DIR` when set. This is the directory Antigravity CLI reads global customizations from, and it must already exist. Install writes `hooks/muster-agent-state.sh` (or `muster-agent-state.ps1` on Windows) and adds a Muster-owned `muster` block to `hooks.json`. Antigravity CLI keys `hooks.json` by hook name, so install rewrites only that block and leaves other named hooks untouched. Uninstall removes the `muster` block and deletes the hook script.

This session-only integration reports the pane's current conversation, but not agent state. Muster keeps deriving working, idle, and blocked from what Antigravity CLI draws on screen.

The hook runs on `PreInvocation`, so Muster learns the conversation once the first prompt is sent. From then on Muster can resume the pane with `agy --conversation <id>` after a Muster server restart.

## Grok CLI

Install the Grok CLI hook:

```bash
muster integration install grok
```

The hook reports session identity through Grok's `SessionStart` hook while Grok CLI runs inside a Muster pane. Grok state comes from Muster's screen manifest detection.

Muster uses `~/.grok` by default, or `GROK_HOME` when set. The Grok config directory must already exist. Grok merges every `hooks/*.json` file in that directory, so install writes a self-contained `hooks/muster.json` with the Muster `SessionStart` entry next to `hooks/muster-agent-state.sh` (`hooks/muster-agent-state.ps1` on Windows), and never edits other hook files. Uninstall removes exactly those two Muster-owned files.

After Grok emits a session start event, Muster can use the reported session id to resume the pane with `grok --resume <id>`.

## Custom status labels

Integrations report lifecycle state as semantic state only. For example, report an agent as `working` without adding display fields to the lifecycle report.

```bash
muster pane report-agent w1:p1 \
  --source custom:docs \
  --agent docs-bot \
  --state working
```

User hooks that run next to a Muster-managed integration should use metadata instead of `report-agent`. Metadata changes presentation without taking over the integration's `idle`, `working`, `blocked`, or session restore authority. `--agent` and `--applies-to-source` guard only presentation fields (`--title`, `--display-agent`, and `--state-label`). Token patches always apply; their reporter owns clearing or TTL refresh. `--display-agent` changes the visible name.

```bash
muster pane report-metadata "$MUSTER_PANE_ID" \
  --source user:claude-title \
  --agent claude \
  --title "Refactor auth middleware" \
  --display-agent "Claude: auth" \
  --token summary="refactor auth" \
  --state-label working="refactoring auth" \
  --ttl-ms 3600000
```

Tokens and state labels are visual-only. Waits, notifications, and workspace rollups still use the semantic state.

## Debug integration state

List known agents:

```bash
muster agent list
```

Read a pane when you need to verify what Muster can see:

```bash
muster pane read w1:p1 --source recent --lines 50
```

If integration state looks wrong, first confirm the agent is running inside Muster and that the relevant hook or plugin was installed for the same user account.
