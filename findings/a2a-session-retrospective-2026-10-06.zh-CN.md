## 分工协调发现

### F02：研究任务缺少明确的阶段交付

**事实。** 研究分派要求最终报告，但两轮都没有留下最终研究报告。第二轮已有源码检查进展，回收后由主控重复核对并补写 controller research。可见依据为 S01:766、859、987、1054，对应 E02–E05。

**协调层缺口。** 任务合同没有明确可保留的中间产物、阻塞说明和移交条件，使下一负责人难以直接接续已完成的研究。这里关注任务如何交付与移交，而不是模型何时结束对用户的回合。

**行为归属。** 主控把 `done` 说成研究完成、依赖等待时长决定中断，属于具体的主控判断，详见[模型行为记录](gpt-behavior-2026-10-06.zh-CN.md)。这些判断本身不能证明 Herdr 有缺陷，也不能证明 worker 挂起。

**已有处置与缺口。** 后续开发 worker 能交付冻结源码与测试记录，程序也将显式 submit 和 pane 回收分开。研究任务仍需约定阶段产物，并在移交或回收时保留目标身份、最近进展、现有产物和处置依据。跟进：[T-012](../.project-map/tickets/T-012-research-handoff.md)。

### F03：项目治理规则反复落到了不适用的夹具目录

**事实。** 三个真实分页 worker 都读取了上层 a2a 规则，又在自己的隔离 worktree 执行 project-map status，得到 `.project-map/MAP.md not found; run init`。可复核实例分别为 S07:38、S16:47、S18:50，对应 E09–E11。后续还出现重复的同类检查。

这些 worktree 本来只有分页 starter 和 CONTRACT。它们是受管实验的任务仓库，不是 a2a 项目地图的副本。worker 没有擅自创建第二套地图，这一点是正确的。

**影响判断。** 缺少明确的“任务仓库、治理根目录、适用规范、交付入口”对应关系，使 worker 自行判断规则范围。无效检查成为重复噪声，也可能将真实阻塞与不适用的检查混在一起。

**缺口。** 当前 prompt 有 workspace、base、身份与 submit 命令，但还不足以明确这些治理边界。应先定义并检查任务范围，不能简单复制所有主项目规范到每个夹具。跟进：[T-013](../.project-map/tickets/T-013-fixture-governance-scope.md)。

**边界与缺口。** 三个子审查都留下了完成结果，本次没有发现它们造成错误集成或持续运行泄漏。问题是配置与资源记录不完整，不是已证实的模型质量问题。下轮应记录完整 session 树，并明确允许的审查角色和模型例外。跟进：[T-010](../.project-map/tickets/T-010-descendant-session-accounting.md)。

**影响判断。** monitor 作为临时观察者发挥了作用，但观察结束后缺少负责人接收、逐项处置和覆盖确认。完整 session 让这次事后核对成为可能，没有自动补上当时缺失的独立监控。

**缺口。** 应分别检查观察任务是否交付、发现是否有处置、覆盖范围能否支撑声明。产品验收 PASS 与监控覆盖完整是不同结论，不能用一项替代另一项。跟进：[T-011](../.project-map/tickets/T-011-monitor-closure.md)。

## 工程与证据处理发现

### F06：证据采集代码本身反复失败

**事实。** 基线 monitor 使用当前 Python 不支持的 `Path.write_text(..., newline=...)`，写报告时抛出 TypeError（S03:104，E17）。T-007 的首轮故障夹具读取持久 intent 失败，产生 5 项 fixture error，不能作为产品业务红态（S10:82，E18）。T-008 还保留了诊断 Path 无法 JSON 序列化、观察屏障同时阻塞 controller reclaim 的夹具错误。

**已有处置。** 作者分别修正了写文件方式、状态观察器、诊断表示和一次性屏障。T-007 最终父版是 4 项业务失败、5 项通过、0 项夹具错误。T-008 使用修正后的有效 mutant 结果，旧错误没有冒充产品反证。见[恢复结果](../evidence/2026-10-06-recovery-01/RESULTS.md)与[自动运行结果](../evidence/2026-10-06-run-01/RESULTS.md)。

**缺口。** 每次修复都有效，但采集脚本的环境兼容、序列化和故障分类仍主要靠现场发现。应在成本更高的真实模型运行前检查证据采集是否可用，并用故意损坏的采集器证明它不会产出产品 PASS。跟进：[T-014](../.project-map/tickets/T-014-evidence-preflight.md)。

### F07：大段输出与错误归档方式妨碍复核

**事实。** 研究阶段多次读取大段源码与工具输出，记录中出现截断。后续一次工具结果明确报告原始输出约 115,063 tokens 并截断（S01:2178，E20）。这不是实际计费 token 的测量。

同一阶段，`git add` 对内嵌测试仓库给出 embedded repository 警告（S01:2164，E19）。这些目录曾以 gitlink 形式进入本地提交，不能替代完整、可携带的实验现场。

**已有处置。** 后续保留原目录，将 Git 对象、SQLite 和源码快照封装为归档，并移除错误的 gitlink 登记。最终结果记录了修正过程，没有删除旧失败证据。

**缺口。** 应先保存完整原始输出，再提取必要摘要；提交证据前检查归档是否包含所需内容、索引中是否误入 gitlink。不能将“文件已提交”直接当作“实验可重建”。跟进：[T-014](../.project-map/tickets/T-014-evidence-preflight.md)。
