## 主要发现

### F01：忙碌时输入后，交付停住，界面没有说明发生了什么

- 类别：工程与证据处理、界面与交互。严重程度：阻断（本次 T-103 旅程）。
- 现象：T-103 在运行 Stop hook、窗格显示“忙”时收到人工输入，随后 CLI 明确回复并显示 done，但侧栏为“未知”，窗格头仍“忙”，门禁保留已认领、候选尚未交付。没有给用户显示明确拒绝原因或可操作的恢复入口。
- 复现：派发首版只写“草稿”的小票；看到运行 Stop hook 时在该 worker 窗格提交一条不改变任务范围的说明；等 CLI 回复完成；对照侧栏、窗格头与门禁；打开窗格菜单找恢复入口。
- 证据：[输入前忙碌](../evidence/2026-10-23-batch24/T-155/screenshots/37-worker-c-busy-before-input.png)、[输入后未知](../evidence/2026-10-23-batch24/T-155/screenshots/39-input-during-stop-unknown.png)、[窗格菜单](../evidence/2026-10-23-batch24/T-155/screenshots/40-unknown-pane-menu.png)。复盘包另记录 `worker_not_active`，属于事后模型对包内数据的解释，仍待停止后的独立读回。
- 为什么不合理：真实用户看到 agent 已答完，却无法判断该等、重交还是恢复；盲目重发还可能制造重复或过期交付。保护未知状态是必要的，但需要把最后确定事实、拒绝原因和下一步说清楚。
- 建议：先明确 Stop 与用户输入相交时的交付语义，再提供绑定原 attempt 的可核对状态与恢复操作。本票不建议用自动重试掩盖结果未知。
- 限制：目前只在第二实例出现一次；未宣称稳定复现，也未宣称所有人工介入都会阻断。

### F02：只读查看会触发“输入尚未确认”的错误横幅

- 类别：界面与交互。严重程度：一般。
- 现象：点击两个独立审查员，未键入任何字符，都显示 `a2a:focus-observation: Window is not available for input`。任务卡修订后，点击两个只读历史 worker 也出现同一横幅。
- 复现：在侧栏打开独立审查员或已失效 attempt 的历史 worker；只看，不输入。
- 证据：[审查员 A](../evidence/2026-10-23-batch24/T-155/screenshots/33-reviewer-focus-error.png)、[审查员 B](../evidence/2026-10-23-batch24/T-155/screenshots/34-second-reviewer-readonly-error.png)、[历史 worker](../evidence/2026-10-23-batch24/T-155/screenshots/50-revoked-worker-a-idle.png)。
- 为什么不合理：只读是预期能力，查看操作却报告输入失败，容易让用户以为审查或交付被自己打断。终端仍可阅读，不等于整个查看动作正常。
- 建议：只读窗格不要申请可写输入焦点；保留清晰的只读说明，真正发生输入失败时才提示错误。

### F03：“向右分屏”实际切到新普通终端，原 worker 没有并排保留

- 类别：界面与交互。严重程度：严重（影响同时观察多个会话）。
- 现象：在 T-101 任务的 worker 菜单点击“向右分屏”，主区只出现一个新普通终端，目录为项目根目录。原 worker 不在画面中；页面标题和门禁条仍显示 T-101。
- 复现：选择 T-101 任务；打开其 worker 窗格菜单；点向右分屏；核对窗格数、类型、工作目录和任务标题。
- 证据：[分屏结果](../evidence/2026-10-23-batch24/T-155/screenshots/41-task-split-result.png)，动作前后的 AX 记录见逐场记录。没有向新终端输入命令。
- 为什么不合理：操作名让用户预期保留当前会话并增加右侧窗格；实际改变了会话类型和目录，还保留旧任务上下文，容易输错地方。
- 建议：按当前视图明确分屏对象；保留原窗格。任务 agent 与项目普通终端若不能组合，应在操作前说明，而不是隐式切换。

### F04：角色批准不出现在“用户输入记录”里

- 类别：工程与证据处理。严重程度：一般。
- 现象：页面说明称字、答复和审批都会记录。两个实例都在界面批准了执行主控，但记录页没有该批准，只出现批准后主控提示、worker 输入和问题答复。
- 复现：全新隔离实例打开新项目；CLI 申请主控；界面批准；确认生效后打开记录页，保持全部任务、全部会话筛选。
- 证据：[实例 1 记录页](../evidence/2026-10-23-batch24/T-155/screenshots/09-records-after-role.png)、[实例 2 记录页](../evidence/2026-10-23-batch24/T-155/screenshots/35-records-human-interventions.png)。实例 1 停止后的数据库副本中，`role_request_decided` 与 `role_request_confirmed` 均存在，`user_inputs` 仅有 C2、C3 两条 message；不是批准事实完全丢失。
- 为什么不合理：统一输入视图无法追溯这次关键授权，与页面说明及项目“批准/拒绝属于用户输入”的术语不一致。另有角色事件不等于这个页面已经覆盖。
- 建议：批准/拒绝进入统一输入记录并关联角色申请事件；若页面有意排除此类操作，应收窄说明并提供明确的授权记录入口。
- 新实例复核：这是两个全新 root、同一产品版本的重复观察；第二实例的停止后独立读回尚待补齐。

### F05：任务卡修订后，重试仍被旧 attempt 的路径占用挡住

- 类别：工程与证据处理、界面与交互。严重程度：严重。
- 现象：`card_save` 保存 v2 不会自动改已注册合同；此规则本身有文档。主控从 `a2a help` 没找到采用新卡的步骤，须测试者指向公开 README 的 `revise`。两票 revise 成功、旧 attempt revoked、current_attempt 为空后，新 dispatch 仍分别被自己的旧 attempt 以 `path_overlap` 拒绝。继续还需要选择是否明确允许交叠，并再次人工核对旧窗格空闲；完成这些额外步骤后，两票 a2 确实派发成功，不能说它们永远无法重试。
- 复现：独立审查打回弱完成条件；主控保存同目标 v2；按 README 显式 revise；尝试正常 dispatch；对照冲突中的旧 attempt 身份。
- 证据：[修订前拒绝](../evidence/2026-10-23-batch24/T-155/screenshots/44-controller-bounded-diagnosis.png)、[修订后冲突](../evidence/2026-10-23-batch24/T-155/screenshots/48-revise-progress.png)、[额外核对](../evidence/2026-10-23-batch24/T-155/screenshots/49-retry-queue-check.png)。
- 为什么不合理：用户认为已按公开文档结束旧执行所有权，却仍需理解底层路径占用与交叠参数才能重试。保留旧现场是正确要求，不应让“保留证据”与“仍占用任务路径”难以区分。
- 建议：明确修订、旧会话处置和路径释放的完整用户流程，给角色使用说明提供可发现步骤；不能简单取消路径检查。当前只报告本轮的阻断和人工成本，不推断所有修订都不可恢复。

### F06：指标里的回合数不能作为本轮总预算

- 类别：工程与证据处理。严重程度：一般。
- 现象：指标页一度显示 managed 会话合计 14 回合，结束时为 9 会话、22 回合，主控却始终为模型 unknown、回合 0；实际已有多条批准后的主控输入与完成回复，另外还有一次真实 Reflect。有实际打回时，页面的“打回原因”仍显示无数据，未解释当前汇总分母。
- 复现：批准主控后提交至少两轮任务指令并等结束；打开记录页核对提示，再打开指标模型使用表。
- 证据：[真实输入记录](../evidence/2026-10-23-batch24/T-155/screenshots/35-records-human-interventions.png)、[指标](../evidence/2026-10-23-batch24/T-155/screenshots/45-metrics-with-real-turns.png)。
- 为什么不合理：unknown 是诚实的模型标记，但把不可完整计量的主控回合显示为 0，会让用户低估总量。主控也多次说明无法取得全局预算。
- 建议：区分已核对的零与未知/未覆盖，说明是否含项目终端、人工输入、回执与复盘；提供可重放的逐会话计数来源。本票不会把看板 14 报成全局总回合。

### F07：同一任务的问题编号重复，主控身份又不在窗格头显示

- 类别：界面与交互。严重程度：轻微。
- 现象与复现：T-102 的 worker 分组问题与 system 审查协议问题同时显示“问题 1”；查看同页两卡可见。另一个现象是角色确认后，侧栏叫执行主控，窗格头仍是普通终端，收起侧栏后缺少持续的角色标识。
- 证据：[两个问题](../evidence/2026-10-23-batch24/T-155/screenshots/36-review-problems-and-duplicate-numbers.png)、[第二实例主控](../evidence/2026-10-23-batch24/T-155/screenshots/24-role-confirmed-header.png)。旧实例的图 15 也有相同身份标题现象。
- 为什么不合理：多会话沟通时，“T-102 问题 1”不能唯一指向一条记录；普通终端是载体类型，执行主控是当前角色，界面只在侧栏区分，辨认成本偏高。
- 建议：界面展示项目/任务范围内可唯一定位的短编号；窗格头同时显示载体与已确认角色。没有把标题差异误报为权限未生效。

## 在已查范围内未发现问题的环节

- 项目目录选择、新建终端和指定命令启动 CLI 均实际完成；只信任一次性 repo，没有登录或系统隐私操作。
- 角色申请的编号卡片与窗格框对应；批准先显示等待确认，确认后侧栏成为执行主控。两实例都走到，没有把 granted 当权限已生效。
- 第二实例两个 worker 确实同时运行，挂在执行主控下面；两个 reviewer 随后在流程页各自进入独立审查列。未用终端 idle 或模型完成宣称交付已通过。
- T-102 问题页发送答复后显示已送达，正确 worker 终端出现该答复并确认。记录页把键入、回车与面板答复分开留存；没有把这些原始行数直接解释成独立业务决策次数。
- 机械检查没有替代独立审查。弱验收被打回，协议无效被暂停，未集成候选没有被伪称成功。
- Reflect 确实生成中文报告和 8 条待决定建议，记录为已完成；没有批准或执行建议。建议是模型输出，不能充当本报告的独立证据。

## Herdr 对照（阶段结论）

| 体验项 | 结论 | 实际检查与限制 |
| --- | --- | --- |
| 开 agent | 部分 | 主控确能同时派出两个 Claude worker，再新开两个 reviewer；正常首次派发已跑通，但失败后的卡修订与路径释放需要多轮提示和人工选择。未测 Codex worker。 |
| 看到谁在干什么 | 部分 | 侧栏父子关系、角色和流程阶段可见；主控窗格名、只读输入告警与未知/忙冲突降低可辨认性。 |
| 切换 | 部分 | 侧栏能进入正确 worker、reviewer 与历史会话；分屏未实现预期的保留原窗格并排显示，终端重叠显示的根因未验证。 |
| 盯进度 | 部分 | 流程页能看到并行与审查；项目总览为任务大卡，不显示两个任务的实时终端；T-103 未知交付缺少下一步。 |
| 回复 | 部分 | 问题答复实际进入正确 worker，人工介入可追溯；Stop 期间输入导致本轮交付停住，系统协议错误只展示原始 JSON，恢复成本高。 |

这是日期记录与探索性基线，不作可靠性、性能、成本或改进收益主张。任务打分与集成未走到：两票被审查协议暂停，一票交付未知。后续仅补 UI 重开、停止后读回、证据归档与报告独立审查；不再通过新增模型回合掩盖本次失败，未走到的步骤保留 INCOMPLETE。
